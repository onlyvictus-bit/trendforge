### How to Wire This Into Your UI (The "Header" Concept)

Based on your request, the Radar UI should group the output of these screeners using the Sector/Macro momentum as a literal "Header".

**Example UI Layout:**

> **[ HEADER: NIFTY METAL (+3.2%, Volume 2x Avg) ]** *(Sector Gainer)*
> *   **TATASTEEL** (Intraday) | Vol: 4x | Block Deal: Yes
> *   **HINDALCO** (Swing) | Delivery: 65% | Announcment: Yes
> *   **JSWSTEEL** (Options) | OI Change: +12% | Vol/OI: 1.8
>
> **[ HEADER: GLOBAL CRUDE (EIA Drawdown, USD Weak) ]** *(Macro Gainer)*
> *   **MCX CRUDEOIL** (Commodity Swing) | MCX Vol: 3x | Macro Align: Yes
>
> **[ HEADER: NIFTY IT (-1.5%, Sector Loser) ]** *(Sector Loser - Short Candidates)*
> *   **INFY** (Intraday) | Vol: 2x | Price: -2% | Large Deal: Sell

### Why this is the "Best of Best" Design:
1.  **Context over Isolation:** You never look at a volume gainer in isolation. You look at it *because* its sector is moving. This filters out 80% of false breakouts.
2.  **Respects API Limits:** By using EOD bhavcopy (`nse_bhavcopy_eod`) for volume baselines and live APIs (`nse_volume_gainers`) for today's pulse, you avoid hitting rate limits. You only query the live option chain for Screener 3 candidates.
3.  **No Intent Inference:** The screener tells you "TATASTEEL has high volume and Metal sector is up." It does *not* tell you "TATASTEEL is bullish because dealers are short gamma." It leaves the directional decision to your closed-bar price structure logic.
4.  **Separated Timeframes:** A day trader looks at Screener 1. A swing trader looks at Screener 2. An options trader looks at Screener 3. They don't step on each other.

-- Multi-Gate Screener: 'Institutional Accumulation + Volume Breakout'
SELECT
  u.symbol,
  p.close_price,
  p.delivery_pct,
  v.volume_1w_change,
  sast.post_event_holding - sast.pre_event_holding AS promoter_delta,
  fii.net_value_crore AS fii_flow,
  oi.pcr,
  asm.security_name IS NULL AS asm_clear,
  pledge.pledge_pct < 20 AS pledge_safe
FROM nse_equity_universe u
JOIN nse_bhavcopy_eod p ON u.symbol = p.symbol
JOIN nse_volume_gainers v ON u.symbol = v.symbol
LEFT JOIN nse_regulation_29 sast ON u.symbol = sast.symbol AND sast.side = 'BUY'
LEFT JOIN nse_fii_dii fii ON fii.date = CURRENT_DATE
LEFT JOIN nse_option_chain_equity oi ON u.symbol = oi.symbol
LEFT JOIN nse_asm asm ON u.symbol = asm.symbol
LEFT JOIN nse_pledge_data pledge ON u.symbol = pledge.symbol
WHERE asm.security_name IS NULL          -- ELIGIBILITY: Not under ASM
  AND pledge.pledge_pct < 20             -- ELIGIBILITY: Low pledge
  AND p.delivery_pct > 60                -- FLOW: High delivery = accumulation
  AND v.volume_1w_change > 200           -- FLOW: Volume spike vs 1W avg
  AND sast.post_event_holding > sast.pre_event_holding  -- SPONSOR: Promoter buying
  AND fii.net_value_crore > 0            -- SPONSOR: FII net positive
  AND oi.pcr > 1.0                       -- FLOW: Put-call ratio bullish
ORDER BY p.delivery_pct * v.volume_1w_change DESC
LIMIT 20;

The supplied HTML documents a high-fan-out orchestrator that calls source monitor, parser, gates, safety, calendar, market context, OHLCV, lifecycle, evidence, causal, and storage. Decompose it into typed in-process stages, but do not assume microservices are required.

6.2 Hybrid parallelism requires barriers

The proposed “stream every symbol directly into final causal scoring” is unsafe where calculations are cross-sectional.

Required barriers:

B0: freeze run manifest and PIT universe
B1: complete/close discovery feature collection for the comparable cohort
B2: build cross-sectional baselines and ranks
B3: parallel per-symbol structure/evidence/options enrichment
B4: reconcile dataset-root correlation and any cross-symbol penalties
B5: revalidate dynamic safety/eligibility
B6: atomically publish run

Per-symbol work can run concurrently between barriers. Final rank, family independence, and public state must not depend on task completion order.

The claim that runtime becomes O(n/workers) is an oversimplification because request budgets, serial exchange constraints, barriers, database writes, and slowest-task latency remain.

6.3 Radar consistency

The documented radar selects the latest run by started_at, not the latest completed run. Correct this with:

run_id and explicit lifecycle;

atomic publish/commit marker;

latest_complete_run_id for stable radar;

separate optional live-progress endpoint for partial runs;

no merging of partial and completed candidates without clear labels.

6.4 run_hash is insufficient lineage

The documented hash is the first 16 hexadecimal characters of SHA-256 over universe, trigger, and timestamp. This is useful as a short display identifier but not sufficient for:

decision-input identity;

idempotency;

replay equality;

source snapshot lineage;

configuration equivalence.

Use separate fields:

run_id              UUIDv7 or equivalent unique identifier
request_id           API idempotency/request identity
manifest_hash        hash of immutable run configuration
input_bundle_root    Merkle/content root over source snapshot IDs
publication_id       immutable published result revision
short_display_id     optional truncated human-readable ID

6.5 Demo data isolation

TRENDFORGE_DEMO_MODE can return mock rows when radar is empty. Require:

separate demo endpoint or explicit data_class=DEMO;

permanent visible DEMO banner;

no export, journal, replay, or downstream evidence use;

no mixing with actual candidates in one response;

disabled by default.

The other AI assumes POST /api/scanner/run-once blocks for minutes. The HTML documents a background scheduler thread but does not prove the run-once HTTP behavior. Inspect actual route and scheduler code before changing it.

If blocking is confirmed, return 202 Accepted with run_id; otherwise preserve the existing non-blocking behavior.

16. Disposition of the Gemini v7.1 Review

16.1 Overall verdict

The review correctly recognizes the strongest parts of CIE v7.1: observed-versus-modeled separation, removal of legacy score/state authority, elimination of universal operational constants, and subordination to the single parent options_intelligence package. Its operational concerns are worth testing, but its proposed remedies must not be adopted literally. Three recommendations would convert explicit uncertainty into apparently usable modeled data and would therefore weaken the governing fail-closed contract.

16.2 Claim-by-claim disposition

Gemini claim or proposal

Decision

Correct architecture treatment

Missing dividends will stall the entire pipeline

PARTLY INCORRECT

Missing dividend input disables only affected carry-dependent calculations. Raw quotes, OI, volume, coverage and other independent facts remain visible. V7.1 already permits zero yield only when explicitly justified and stored as an assumption.

Add SCENARIO_ASSUMED_ZERO_YIELD so calculations continue

LIMIT TO DIAGNOSTIC RESEARCH

A zero-yield scenario may be displayed as SCENARIO_ONLY, but it must not silently replace the governed carry input or support state eligibility. Preserve the observed/assumed distinction and compare sensitivity against alternative carry scenarios.

Strict {} handling is brittle

API drift is expected and must be isolated by a versioned source adapter and schema-recovery workflow. Add an API translation layer

ALREADY REQUIRED / CLARIFY

No extrapolation will often yield unknown skew

TRUE AND INTENTIONAL

Thin or incomplete wings should produce SKEW_COVERAGE_UNKNOWN on the governed v1 path. Uptime is not improved by manufacturing a 25-delta node outside observed support.

Parent ownership creates excessive coupling

NOT AN ARCHITECTURAL ERROR

Memoize Black-Scholes intermediate values aggressively

First benchmark and vectorize calculations. Safe caching should be deterministic and keyed by the complete immutable input contract: snapshot bundle, symbol/contract identity, strike, expiry/time, spot/forward, IV, rate, dividend, model version and formula profile. “Not materially changed” tolerance caching is unsafe on a state path because it can create stale, order-dependent results. Prefer per-snapshot/per-run exact-key memoization and bounded caches.

16.3 Dividend behavior must be feature-scoped

The correct behavior is not “missing dividend means the complete CIE pipeline stops.” It is:

Observed market facts not requiring carry
    -> remain available with their own quality status

Parity, forward, Delta-coordinate, IV or other carry-dependent outputs
    -> DIVIDEND_INPUT_UNKNOWN / UNKNOWN / WAIT as required

Explicit zero-yield assumption
    -> separately labeled scenario
    -> assumption source and justification stored
    -> not silently state-eligible

This feature-scoped eligibility prevents both extremes: silent zero-yield invention and unnecessary loss of every independent observation.

16.4 Source-adapter boundary

The adapter must normalize syntax without falsifying semantics:

HTTP/session result
 -> sanitized native archive
 -> transport/content/schema classification
 -> source-specific envelope adapter
 -> versioned normalized contract
 -> feature eligibility

Required separate result classes include valid non-empty, contract-proven valid empty, timeout, DNS/TLS, authentication/block, rate limit, maintenance/HTML, malformed payload, schema mismatch, identity conflict, partial coverage and stale cache. No middleware may collapse these into a generic empty response.

16.5 Extrapolation policy

For the governing RR25/Fly25 v1 contract, keep bracketed total-variance interpolation and no extrapolation. A future research-only extrapolation study must have a different method ID and output class, for example:

RR25_EXTRAPOLATED_RESEARCH_V0
eligibility = DIAGNOSTIC_ONLY
state_contribution = 0

It must expose extrapolation distance, wing, nearest observed nodes, fitted method, residuals, sensitivity band, liquidity state and comparison with the non-extrapolated unknown outcome. Promotion requires PIT archives, OOS incremental value and explicit governance approval.

16.6 Greek-engine performance policy

Do not prescribe memoization before profiling. The optimization order should be:

characterize correctness and current latency;

batch/vectorize strike and expiry calculations;

remove duplicate solver calls inside one snapshot bundle;

add exact-key per-run memoization;

bound memory and record cache-hit/miss/eviction metrics;

add broader cache only after proving freshness and deterministic replay;

consider process-level parallelism only after measuring CPU, serialization and storage contention.

Cached outputs must carry the same formula/model/input versions and lineage as newly computed outputs. Cache reuse cannot hide changed time-to-expiry, carry, contract master, corporate action, quote timestamp or IV input.

16.7 Latency-budget answer

No approved maximum latency budget in milliseconds has been established. This is intentional, not an omission to fill with a guessed number. V7.1 rejects fixed latency gates as universal truth, and v9.2 states that budgets, concurrency, timeouts and scale limits must be calibrated from observed source and runtime behavior. The governing plan also deliberately omits time estimates until code characterization and source observations exist.

Add the following unresolved contract:

surface_latency_budget_status = UNSET_PENDING_MEASUREMENT
owner = Options Intelligence parent package
promotion_gate = OI-1 + OI-3 + OI-8 observations complete

The measurement plan must report, by source profile, market phase, DTE/liquidity bucket and universe size:

fetch/session latency separately from CPU calculation latency;

normalization, identity, carry, parity, IV, Greeks, surface, flow, fusion and persistence durations;

p50, p95, p99 and worst bounded latency;

cold-cache and warm-cache behavior;

cache hit/miss/eviction and memory use;

symbols planned, attempted, completed, partial and not attempted;

request-budget exhaustion and breaker effects;

one liquid index plus five-stock thin vertical first, then measured 50/100/250 scale tests.

Only after these observations should the parent approve a versioned total-cycle budget and stage allocations. If a budget is exhausted, remaining symbols become explicit partial/not-attempted results such as WAIT_RATE_LIMIT_BUDGET_EXHAUSTED; the system must not lower quality checks to meet a latency target.

16.8 Audit conclusion on the Gemini review

Adopt the review's request for performance profiling, deterministic caching analysis, adapter isolation and contract-version protection. Do not adopt assumed-zero carry as ordinary evidence, semantic translation of failures into empty data, a fixed three-Delta extrapolation allowance, or a guessed latency target. The correct strengthening is graceful degradation with honest feature-level unknowns, not increased uptime through invented inputs.

19. Lane-Separated Scanner Architecture and Sector-First Routing

19.1 Correction to the previous source map

The previous 105-link usage map grouped sources mainly by technical function. That is useful for data governance, but it is not the correct product organization for the scanner. The implementation must expose separate lane contracts for:

Equity Intraday;

Equity Swing;

Equity Position;

Options;

Commodity Intraday;

Commodity Swing.

A source may serve several lanes, but its timing, authority and semantic role must be different in each lane. For example, an EOD bhavcopy may be a primary historical baseline for swing research, but it is only a baseline or fallback in an intraday lane and must never be displayed as live flow.

The revised row-by-row implementation matrix is in TrendForge_105_Link_Usage_Map.xlsx.

19.2 Sector first, stock second

For equity intraday and options-underlying discovery, the required hierarchy is:

MARKET HEADER
  -> SECTOR GAINER / LOSER / NEUTRAL HEADER
      -> STOCK ACTIVITY CANDIDATES
          -> SECTOR-ALIGNED OR COUNTER-SECTOR BUCKET
              -> TRADABILITY
                  -> LANE-SPECIFIC DEEP ANALYSIS

The primary source roles are:

nse_all_indices
  -> market and sector movement board

nse_volume_gainers
nse_most_active_volume
nse_most_active_value
nse_variations_gainers
nse_variations_loosers
  -> stock candidates displayed below their mapped sector header

The scanner must not display one flat volume-gainer list without sector context.

19.3 Correct use of volume gainers

Volume gain is an activity fact, not direction. A volume-gainer row must be combined with:

stock price direction;

mapped sector direction;

sector breadth;

stock relative strength or weakness versus the sector;

current tradability and liquidity;

event/catalyst evidence when the stock opposes its sector.

The initial routing buckets are:

Bucket

Sector relationship

Use

ALIGNED_LONG

sector gaining, positive breadth, stock rising and outperforming

highest long-research priority

ALIGNED_SHORT

sector losing, negative breadth, stock falling and underperforming

highest short-research priority where eligible

COUNTER_SECTOR_LONG

weak sector, stock rising strongly

separate outlier queue; requires catalyst or independently proven relative strength

COUNTER_SECTOR_SHORT

strong sector, stock falling strongly

separate outlier queue; requires negative catalyst or risk evidence

NEUTRAL_ACTIVITY

sector mixed, stale or unknown

lower priority or named WAIT

Sector alignment should prioritize candidates, but it must not become an absolute rule that deletes every stock moving against its sector. Counter-sector stocks may be important leaders, reversals or event-driven moves; they need separate treatment because their fakeout risk and causal burden are higher.

No fixed percentage or breadth threshold is approved as universal truth. Sector ranks, breadth profiles, liquidity profiles and persistence rules must begin as versioned hypotheses and be validated PIT/OOS.
